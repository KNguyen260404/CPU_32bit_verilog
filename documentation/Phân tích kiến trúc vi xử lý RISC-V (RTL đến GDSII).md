# <a name="header"></a><a name="content"></a><a name="x863595adf5021d8cc062330c20e3824e4d6b12a"></a>Kế hoạch kiểm thử cho bộ vi xử lý RV32I (đơn chu kỳ)
## <a name="phạm-vi-kiểm-thử"></a>1. Phạm vi kiểm thử
- **Nhóm lệnh RV32I:** Bao gồm các lệnh số học và logic (R-type/I-type): ADD, SUB, SLL, SLT, SLTU, XOR, SRL, SRA, OR, AND và các bản ngay (immediate) tương ứng (ADDI, SLLI, SLTI, SLTIU, XORI, SRLI, SRAI, ORI, ANDI). Các lệnh **Load/Store:** LB, LH, LW, LBU, LHU, SB, SH, SW. Các lệnh **Branch:** BEQ, BNE, BLT, BGE, BLTU, BGEU. Các lệnh **Jump:** JAL, JALR. Các lệnh **Upper Immediate:** LUI, AUIPC. Mỗi nhóm lệnh này tác động khác nhau tới ALU, bộ thanh ghi, và bộ nhớ nên cần test riêng biệt[\[1\]](https://ibex-core.readthedocs.io/en/latest/03_reference/coverage_plan.html#:~:text=%2A%20Branch%20,family%20branch%20instruction).
- **Điều kiện biên và đặc biệt:** Cần kiểm thử các trường hợp như: overflow số học (dù RV32I cộng/trừ theo modulo nên không ngắt tràn nhưng vẫn cần kiểm tra kết quả đúng với 32 bit), truy cập bộ nhớ ngẫu nhiên (kiểm tra đọc/ghi ở địa chỉ biên, ngoài vùng, và căn chỉnh sai) và đảm bảo xử lý hợp lệ theo spec. Đặc biệt, **ghi vào thanh ghi x0:** giá trị ghi phải bị bỏ qua và thanh ghi luôn là 0. Đối với các lệnh có immediate, cần thử nhiều giá trị đặc biệt (ví dụ imm tối đa, giá trị âm, giá trị 0) để kiểm tra việc mở rộng dấu chính xác. Đối với lệnh nhánh, cần xét cả trường hợp nhánh **được thực hiện và không thực hiện** (branch taken/not-taken) nhằm đảm bảo cả hai luồng rẽ. Lệnh JALR cần kiểm tra tính năng đặt PC mới đúng và viết địa chỉ trả về vào rd. Lệnh AUIPC cần kiểm tra cộng PC đúng với hằng số. Các lệnh *load* cần kiểm tra sign-extension và zero-extension (LB vs LBU, LH vs LHU).
## <a name="chiến-lược-kiểm-thử"></a>2. Chiến lược kiểm thử
- **Unit Test (Kiểm thử đơn vị):** Mỗi module riêng lẻ được test kỹ lưỡng. Ví dụ, với **ALU**, thực hiện các testbench cho từng phép toán (cộng, trừ, XOR, AND/OR, SLL, SRL, SRA, so sánh) với nhiều giá trị ngõ vào (đầy đủ bit 0,1, giá trị lớn nhất, nhỏ nhất) và đối chứng kết quả với mô hình tham chiếu. Với **Register File**, thử đọc/ghi các thanh ghi; đặc biệt kiểm tra khi ghi vào x0 phải giữ nguyên giá 0. Module điều khiển (Control Unit) test giải mã opcode, thiết lập các tín hiệu điều khiển đúng. Mỗi testbench đơn vị nên chạy ở mức thấp (instatiate module Verilog, cấp input và kiểm tra output).
- **Integration Test (Kiểm thử tích hợp):** Kết hợp các module thành cụm nhỏ (ALU+RegFile, ALU+RegFile+CU, có thể kèm cả memory model đơn giản). Ví dụ chạy lần lượt các lệnh và kiểm tra trạng thái bộ thanh ghi, bộ nhớ tại mỗi bước. Có thể viết các chuỗi lệnh Assembly ngắn để test, đổ vào bộ nhớ lệnh giả lập và quan sát kết quả. Phương pháp này kiểm tra sự phối hợp giữa các module (ví dụ xem ALU trả kết quả về RegFile đúng, CU cấp đúng tín hiệu và cập nhật PC hợp lý).
- **System Test (Kiểm thử hệ thống):** Nạp chương trình hoàn chỉnh (file nhị phân hoặc hex) vào bộ nhớ, chạy toàn bộ và so sánh kết quả cuối cùng. Ví dụ nạp chương trình tính tổng mảng, kiểm tra số nguyên tố hoặc các thuật toán đơn giản. Kết quả có thể so với mô hình chuẩn (ví dụ trình biên dịch C ra nhị phân cho Spike) để đối chứng. Hệ thống test bao gồm cả kiểm tra luồng điều khiển (branch, jump) và thao tác bộ nhớ.
- **Testbench và công cụ:** Có thể dùng Verilog testbench truyền thống hoặc khung UVM tùy quy mô. Trong testbench, dùng $readmemh để nạp chương trình (xem phần 5) và sử dụng các tác vụ kiểm tra tự động (assertions). Công cụ giả lập: ModelSim, Icarus Verilog hay Verilator đều hỗ trợ. Verilator có tùy chọn --coverage để đo code coverage của RTL, ModelSim có khả năng đo code và functional coverage. Những công cụ này giúp đánh giá mức độ kiểm thử.
## <a name="bảo-đảm-độ-bao-phủ-coverage"></a>3. Bảo đảm độ bao phủ (Coverage)
- **Coverage chức năng:** Để đạt 100% độ phủ chức năng (functional coverage), phải chắc chắn rằng *mỗi opcode* và *mỗi biến thể* funct3/funct7 của lệnh RV32I được test ít nhất một lần[\[2\]](https://www.synopsys.com/content/dam/synopsys/partners/document/risc-v-wp.pdf#:~:text=Functional%20coverage%20definitions%20for%20RISC,V%20ISA%20coverage). Nên định nghĩa coverpoint cho từng lệnh (ví dụ covergroup trong SystemVerilog) nhằm kiểm tra rằng tất cả lệnh thuộc RV32I đều từng xuất hiện trong thử nghiệm. Cần bao quát cả các kiểu dữ liệu (ví dụ để kiểm thử SLT phải thử cả trường hợp số âm và dương). Theo [Synopsys], ideal coverage là rất lớn (tất cả kết hợp thanh ghi, hằng, giá trị dữ liệu), nhưng quy ước “100% cover ISA” nghĩa là mỗi lệnh và biến thể được kiểm thử (không cần đủ mọi giá trị operand)[\[2\]](https://www.synopsys.com/content/dam/synopsys/partners/document/risc-v-wp.pdf#:~:text=Functional%20coverage%20definitions%20for%20RISC,V%20ISA%20coverage).
- **Chiến lược tạo test cases:** Có thể viết thủ công các test lệnh đơn (directed tests) cho từng lệnh và trường hợp đặc biệt, hoặc sinh tự động (random) các chuỗi lệnh. Ví dụ, công cụ *RISC-V DV* (được Google phát triển, dùng trong UVM) tự động sinh các chương trình RISC-V để stress-test vi xử lý[\[3\]](https://www.synopsys.com/content/dam/synopsys/partners/document/risc-v-wp.pdf#:~:text=RISC,and%20many%20of%20the%20extensions). Có thể sử dụng riscv-dv hoặc viết script Python/Perl sinh các tập lệnh ngẫu nhiên thỏa điều kiện (ví dụ các opcode và thanh ghi hợp lệ). Trong testbench, so sánh kết quả với mô hình “vàng” (ví dụ Spike ISS) giúp phát hiện sai khác.
- **Đo lường Coverage:** Dùng metric **code coverage** (statement, branch coverage trên RTL) kết hợp **instruction coverage**. Code coverage đảm bảo từng nhánh trong RTL đã được chạy, còn instruction coverage kiểm tra từng lệnh RV32I đã được thực thi. ModelSim/Verilator có thể tạo báo cáo code coverage; với functional coverage, nếu dùng SystemVerilog, sẽ tạo covergroup. Ví dụ, coverpoint theo opcode hoặc theo loại lệnh. Phân tích báo cáo để thêm test cho các trường hợp chưa cover. Kết hợp code và functional coverage giúp đảm bảo môi trường kiểm thử đầy đủ[\[4\]](https://www.synopsys.com/content/dam/synopsys/partners/document/risc-v-wp.pdf#:~:text=3%20Structural%20code%20coverage%20,This%20resulting%20powerful).
## <a name="gợi-ý-các-chương-trình-kiểm-thử-thực-tế"></a>4. Gợi ý các chương trình kiểm thử thực tế
- **Tổng mảng (Array Sum):** Một chương trình lặp qua phần tử mảng, dùng lệnh LW/SW và phép cộng (ADD) để tính tổng. Bài này test nhóm lệnh Load/Store và Arithmetic. Ví dụ khởi tạo vài giá trị trong bộ nhớ và cộng vào thanh ghi. Kết quả cuối đối chứng được với giá trị tính thủ công.
- **Kiểm tra số nguyên tố:** Với RV32I không có phép chia, có thể kiểm tra số nguyên tố bằng cách lặp và trừ (SUB) hoặc lệnh nhảy (BNE, BLT) để thử chia lần lượt. Chương trình này kiểm tra các lệnh nhánh (both taken/not-taken) và lệnh chuyển hướng (loop). Có thể dùng các BLT vs BLTU để thử so sánh số có dấu/không dấu.
- **Các phép toán bit (Bitwise ops):** Ví dụ hoán vị bit hoặc đếm bit 1. Sử dụng shift (SLL, SRL, SRA), AND/OR/XOR để thao tác bit. Ví dụ, đảo ngược bit trong một số 32-bit hoặc đếm số bit 1. Test chuỗi các phép toán logic và dịch bit, có thể tạo nhiều giá trị đặc biệt (chẳn, lẻ, có nhiều bit 1 liên tiếp).
- **Điều khiển luồng (Branch/Jump):** Viết các hàm giả lập if-else hoặc for-loop dùng lệnh BEQ/BNE và lệnh JALR cho vòng lặp. Ví dụ, for (i=0; i<10; i++) để test branch taken khi i<10 và không taken khi i>=10. Lệnh JAL có thể test bằng một subroutine đơn giản (thiết lập ra). Lệnh AUIPC/LUI dùng để tạo hằng lớn hoặc địa chỉ (ví dụ tính địa chỉ của ô nhớ dựa trên PC).
- **Tình huống kết hợp:** Ví dụ tính cấp số cộng, thuật toán tìm min/max trong mảng, hoặc giai thừa (nhưng giai thừa cần nhân, và RV32I không có mul). Những chương trình này phối hợp nhiều nhóm lệnh và sẽ kiểm tra luồng điều khiển, memory, và ALU liên tục.
## <a name="tổ-chức-file-kiểm-thử"></a>5. Tổ chức file kiểm thử
- **Chia file Testbench:** Có thể tách riêng các testbench: (1) **Test lệnh đơn:** mỗi file chỉ test một vài lệnh cụ thể hay trường hợp cá biệt, giúp debug nhanh. (2) **Test chương trình:** một file khởi tạo bộ nhớ với chương trình nhị phân (hex) rồi chạy toàn bộ, kiểm tra kết quả cuối cùng. (3) **Test tự động (Regression):** tập hợp nhiều chương trình kiểm thử tự động (script hoặc batch) để chạy liên tục, đo coverage.
- **Định dạng file lệnh:** Thường dùng file hex hoặc mem để nạp vào ROM, RAM. Ví dụ, ta có thể lưu chương trình nhị phân (được biên dịch hoặc mã hóa nhị phân) thành file văn bản chứa các giá trị hex (mỗi dòng 32-bit) và dùng $readmemh("file.mem", mem\_array); trong Verilog để nạp[\[5\]](https://stackoverflow.com/questions/43149592/how-to-generate-hex-files-in-risc-v#:~:text=Such%20files%20are%20loaded%20by,bar%2Fvscale%2Fblob%2Fmaster%2Fsrc%2Ftest%2Fverilog%2Fvscale_hex_tb.v). Trong ví dụ từ Vscale, file hex có 32 ký tự hex mỗi dòng (tương đương 4 từ lệnh)[\[6\]](https://stackoverflow.com/questions/43149592/how-to-generate-hex-files-in-risc-v#:~:text=vscale%2Fsrc%2Ftest%2Finputs%20have%20several%20hex%20inputs,add.hex)[\[5\]](https://stackoverflow.com/questions/43149592/how-to-generate-hex-files-in-risc-v#:~:text=Such%20files%20are%20loaded%20by,bar%2Fvscale%2Fblob%2Fmaster%2Fsrc%2Ftest%2Fverilog%2Fvscale_hex_tb.v). Testbench sẽ đọc file đó và gán cho bộ nhớ của DUT, sau đó chạy mô phỏng. Dữ liệu RAM có thể cũng được khởi tạo tương tự nếu cần. Cấu trúc file phải nhất quán với layout memory của bộ xử lý (địa chỉ bộ nhớ lệnh, dữ liệu riêng biệt).

**Tóm lại,** kế hoạch kiểm thử này bao gồm xác định đầy đủ các nhóm lệnh và điều kiện biên, chiến lược từ unit test đến system test, đảm bảo coverage ISA 100% (mỗi opcode/funct được test), sử dụng kết hợp test thủ công và tự động (ví dụ riscv-dv)[\[2\]](https://www.synopsys.com/content/dam/synopsys/partners/document/risc-v-wp.pdf#:~:text=Functional%20coverage%20definitions%20for%20RISC,V%20ISA%20coverage)[\[3\]](https://www.synopsys.com/content/dam/synopsys/partners/document/risc-v-wp.pdf#:~:text=RISC,and%20many%20of%20the%20extensions), đồng thời tổ chức file test rõ ràng (hex/mem) để nạp lệnh vào mô phỏng[\[5\]](https://stackoverflow.com/questions/43149592/how-to-generate-hex-files-in-risc-v#:~:text=Such%20files%20are%20loaded%20by,bar%2Fvscale%2Fblob%2Fmaster%2Fsrc%2Ftest%2Fverilog%2Fvscale_hex_tb.v). Thực hiện đầy đủ các bước này sẽ giúp xác minh tính đúng đắn toàn bộ chức năng của CPU RV32I.

**Nguồn tham khảo:** Tài liệu thiết kế và kiểm thử RISC-V (bao gồm hướng dẫn coverage RV32I[\[1\]](https://ibex-core.readthedocs.io/en/latest/03_reference/coverage_plan.html#:~:text=%2A%20Branch%20,family%20branch%20instruction), mô hình coverage RISC-V[\[2\]](https://www.synopsys.com/content/dam/synopsys/partners/document/risc-v-wp.pdf#:~:text=Functional%20coverage%20definitions%20for%20RISC,V%20ISA%20coverage)) và ví dụ mã nguồn testbench Verilog[\[5\]](https://stackoverflow.com/questions/43149592/how-to-generate-hex-files-in-risc-v#:~:text=Such%20files%20are%20loaded%20by,bar%2Fvscale%2Fblob%2Fmaster%2Fsrc%2Ftest%2Fverilog%2Fvscale_hex_tb.v).
